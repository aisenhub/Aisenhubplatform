# 文档维护规则

当前架构文档描述实际代码、迁移与配置；优化设计和实施计划单独维护。判断当前行为时，代码行为优先于测试断言，测试与配置优先于文档；发现冲突先核对具体实现，再修改对应说明。

## 目录职责

| 目录 | 内容 |
| --- | --- |
| architecture | 已实现的模块、边界、调用链及运行组件 |
| proposals | 优化目标架构、总计划、分阶段计划及其执行状态 |
| decisions | 按需记录重要技术决策 |
| archive | 按明确保留需要归档的失效资料 |
| guides | 现有工具和功能的操作方法 |
| reference | API、配置、数据模型、SDK 和工具链的精确查询 |
| README.md | 文档导航 |
| agents.md | 文档维护规则 |

已有历史资料的清理不限制后续维护优化设计和计划。新优化使用 [proposals 骨架](proposals/README.md)，每项优化建立独立目录：design.md 描述目标架构，plan.md 维护总计划、依赖和阶段状态，phases/ 维护复杂阶段的详细计划。

Proposal 按 Proposed → In Progress → Completed 维护；只有实际开始执行或满足验收条件后才更新状态。每个阶段落地后同步 architecture、reference 和 guides；未实现目标留在 proposal，不提前改写当前架构。完成的 proposal 是否归档或删除按用户要求处理，不自动删除有价值资料。

重要决策按需在 decisions 中记录背景、选择、影响及状态；决策被替代时使用新记录关联旧记录。没有实际内容时无需创建 ADR 或归档文件。执行证据可由计划链接到测试报告，不在当前架构中追加验收流水。

## 更新规则

1. 阅读根 AGENTS.md、本目录导航、相关源码与测试。
2. 核对模块职责、接口、配置、数据库约束、运行入口和页面行为是否变化。
3. 每项事实只保留一个主要来源；其他文档链接引用。完整 SQL 以迁移为准，字段合同以 OpenAPI 和共享类型为准，避免复制整套定义。
4. 区分源码具备的能力、页面演示状态和外部部署事实。只有代码无法证明的生产配置，不写成已部署能力。
5. 修改路径时同步根 README、Agent 入口、脚本、Registry 和文档内引用。
6. 运行 pnpm docs:check 与 pnpm contracts:check；涉及检查器时同时检查语法和负向用例。
7. 整理报告放在任务回复中，不写入 docs。不得写入真实凭据、用户数据、兑换码或文件内容。

文档整理不自动授权功能开发、生产部署或费用变更。
