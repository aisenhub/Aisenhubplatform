# 配置资源系统预研架构

状态：Preliminary Architecture / OPT-007 预研输入，尚未提升为正式 Proposal，也不代表当前系统已经实现。

关联事项：[OPT-007：配置文件系统、配置广场与存储治理](README.md#优化事项总清单)

当前实现参考：[配置文件与持久任务](../../architecture/modules/files-jobs.md)、[权益与订阅](../../architecture/modules/entitlements.md)、[核心数据模型](../../reference/data-model.md)。

## 1. 目标与定位

现有 `config-files` 把配置视为“某个平台账户拥有的私有文件”。后续目标不是继续扩展一个通用文件管理器，而是把配置升级为当前平台内的一种用户内容资源：用户创建并维护自己的配置，提交共享申请；平台管理员审核决定哪些配置可以进入配置广场；只有被管理员准入的配置才会被其他同平台用户发现、点赞、下载或一键应用。管理员负责广场准入/退出、资源治理、存储容量、审核和异常处理，但不因此取得修改用户个人配置内容的权限。

本设计中的“全平台共享”固定解释为：**同一个业务平台内部的全部用户共享，不跨 AisenHub 中的不同平台共享**。不同平台的配置格式、兼容版本、审核规则和商业权益可以完全不同；跨平台配置市场若未来需要，应作为独立架构讨论。

配置系统后续应同时服务三个视角：

- Consumer 用户视角：`我的配置` + `配置广场`。
- 单平台 Admin 视角：配置资源池、作者与发布治理、统计、异常和存储使用。
- 全局 Admin 视角：给各平台分配总存储空间，并观察平台级容量、备份和异常状态。

用户反馈文字与图片不属于本文范围，后续单独设计。

## 2. 核心架构决定

### 2.1 Config 是一等业务对象，File 只是底层载体

后续业务模型不能继续等同于：

```text
用户 -> 上传文件 -> Storage
```

目标模型应改为：

```text
用户 -> 创建 Config -> 创建 Version -> 私有 Storage Object
                 -> 发布/下架
                 -> 点赞/下载/应用
```

`Config` 表示长期存在的“配置作品/配置资源”，应持有标题、说明、作者、发布与审核状态、当前版本以及展示统计。真正的 JSON、INI、二进制配置等内容仍作为不可变文件对象放入私有 Storage，由某一个 `Config Version` 引用。

这一分层解决三个问题：

1. 用户更新配置时不需要覆盖旧对象，而是新增版本。
2. 点赞、发布、审核、标题和统计属于 Config，不应该污染底层文件状态机。
3. 一键应用和问题排查可以明确知道用户使用的是哪个配置版本。

### 2.2 平台内公开不等于 Storage 公开

配置广场公开的是安全的配置 metadata，而不是把 Supabase Bucket 改成 public。

目标读取链路保持：

```text
Consumer Browser
  -> Consumer BFF
  -> AisenHub Account API
  -> Private Storage
```

公开列表只返回允许展示的标题、说明、作者、统计、兼容性等字段。真正下载或一键应用配置内容时，仍经过身份、平台、配置状态和权限检查，不提供永久 Storage URL，也不向浏览器暴露 Storage Secret 或直接写权限。

### 2.3 中央系统分发配置，不解释和执行配置

AisenHub 可以管理配置资源、版本、权限和内容传输，但不应该执行自己不理解的配置 payload。

一键应用的目标边界为：

```text
配置广场
  -> 用户选择“一键应用”
  -> Consumer BFF 获取指定 Config Version
  -> 目标平台验证 schema / app version / payload
  -> 目标平台执行应用
  -> 记录应用结果事件
```

中央层最多验证通用 envelope、大小、hash、平台归属和版本标识。具体字段是否合法、如何写入目标应用，由对应 Consumer 平台负责。

### 2.4 个人配置池与配置广场必须分层，管理员是共享准入门禁

配置广场不是“用户把自己的配置直接切成 public”这么简单。目标模型应明确分成两个业务层：

```text
个人配置池（用户所有）
  -> 用户提交共享申请
  -> 管理员审核
  -> 广场准入记录（管理员治理）
  -> 配置广场公开展示
```

核心原则：

- 用户个人 Config 的所有权始终属于对应 `owner_platform_account_id`；管理员审核广场资格，不接管用户配置所有权。
- 用户只能“提交共享/撤回共享申请/管理自己的配置”，不能绕过管理员直接让配置出现在广场。
- 管理员可以批准进入广场、拒绝申请、将已共享配置移出广场，以及在治理场景下阻止其再次展示。
- “移出广场”只改变共享展示资格，不删除用户个人 Config，也不删除其底层版本/Storage Object。
- 管理员若执行真正的内容删除，必须是独立且更高风险的治理动作，不能把“广场下架”与“删除用户个人配置”合并成同一个按钮或状态。
- 用户更新个人 Config 后，新版本是否自动继续在广场展示不能默认继承；预研建议**新版本重新进入审核**，广场在审核期间继续指向最后一个已批准版本，避免作者在审核后替换成未经审核的新内容。

因此“广场数据库”更适合建模为独立的**广场准入/发布记录（Marketplace Listing / Gallery Entry）**，而不是复制一份新的二进制文件。广场记录引用管理员批准的 Config 与具体 Config Version；真正内容仍只有一份私有 Storage Object，避免个人库与广场库形成双份文件、版本漂移和删除不一致。

## 3. 用户产品模型

### 3.1 我的配置

用户侧应提供“我的配置”区域，至少覆盖：

- 新建配置。
- 查看自己拥有的 Config。
- 上传新版本。
- 编辑标题、说明等可变 metadata。
- 提交进入配置广场的共享申请。
- 查看审核状态与拒绝原因（如允许展示）。
- 在允许的状态下撤回共享申请或请求退出广场。
- 删除配置。
- 查看当前套餐允许的配置数量和当前占用，例如 `1 / 1`、`3 / 10`。

配置数量额度应限制 **Config 实体数量/可用槽位**，而不是历史文件或版本数量。一个 Config 从 v1 更新到 v20，仍只占一个配置槽位。

### 3.2 配置广场

配置广场只展示当前平台**已经过管理员审核准入**的 Config / Approved Version。用户自己的配置即使存在、即使提交过共享申请，只要没有有效的广场准入记录，就不能出现在广场。第一版至少需要：

- 配置名称与说明。
- 作者展示名与头像。
- 发布时间、最近更新时间。
- 当前版本。
- 平台/配置 schema 兼容信息。
- 点赞数量。
- 下载数量。
- 一键应用数量。
- 查看详情、下载、一键应用、点赞/取消点赞。
- 最新、点赞、下载、应用等基础排序。

后续如果需要“本周热门”等综合排序，应基于明确的排名算法和反刷策略，不应在第一版用未经定义的神秘分数。

## 4. 配额与容量模型

现有每账户 `max_file_bytes / max_files / max_total_bytes` 的通用 Storage 配额，不适合目标产品模型。预研建议拆成三类完全不同的约束。

### 4.1 用户配置数量：由 Plan / Entitlement Feature 决定

配置数量是产品权益，应从当前有效权益读取，不在前端硬编码 Free/ Paid 判断。

概念上可以形成类似 feature：

```text
config_slot_limit = 1   # Free
config_slot_limit = 10  # Paid
```

最终 feature key 在正式合同阶段冻结。

现有 `plans.features jsonb` 和 entitlement 返回结果已经具备承载这类能力的基础。配置领域只消费“当前有效配置槽位数量”，不自行判断套餐名称。

套餐降级后若用户已有配置超过新额度：

- 不自动删除配置。
- 不破坏已存在的公开资源。
- 禁止继续创建超额 Config。
- 是否允许为既有 Config 发布新版本，需要在正式架构中冻结；推荐把“新增 Config”和“维护既有 Config”分开，避免降级直接冻结用户现有作品的安全修复能力。

### 4.2 单文件安全上限：后端保护边界

单文件大小限制必须保留，但它不再作为用户套餐卖点，而是安全上限，用于防止：

- Consumer Bug 产生异常巨大 payload。
- 恶意请求耗尽网关、函数内存或 Storage。
- 图片、视频等错误类型被当作配置上传。
- 无界 JSON / 序列化错误。

正常配置可能远小于上限，但 Account API 仍必须在写入 Storage 前验证真实字节数。该限制可以是系统 ceiling，也可以允许平台在安全 ceiling 内设置更小值；不能由浏览器声明大小决定。

### 4.3 平台总存储池：由全局 Admin 分配

新增平台级存储预算，作为当前平台所有配置版本和未结算对象的总容量边界。

全局视角应能够看到类似：

```text
AisenTest   1.3 GiB / 5 GiB
AisenFlow   14 GiB / 20 GiB
```

平台内只展示自己的使用量和剩余量，不允许自行突破中央分配额度。

平台预算统计必须包含所有真实仍占 Storage 或仍有写入不确定性的对象，而不是只统计当前发布版本。`pending / storing / unknown / deleting` 等仍可能占用实际容量的状态必须继续遵守当前“不能猜测释放”的安全原则。

### 4.4 版本增长风险

取消用户字节额度后，一个只有 1 个 Config 的用户仍可能通过频繁上传新版本持续消耗平台总空间。因此正式设计必须额外冻结至少一种防线：

- 配置版本上传速率限制。
- 每个 Config 的版本保留数量/保留时间。
- 旧版本归档或清理规则。
- 平台总空间耗尽后的上传拒绝策略。

无论采用哪种策略，旧版本都不能在新版本成功前被提前删除，也不能为了释放容量猜测未知写入已经失败。

## 5. 建议的数据分层

以下为逻辑模型，表名和字段名在正式 Proposal 阶段再冻结。

### 5.1 Config 实体

建议承担：

```text
config_id
platform_id
owner_platform_account_id
title
description
current_version_id
created_at
updated_at
```

可维护投影统计：

```text
like_count
download_count
apply_count
```

统计字段应视为 Projection / Cache，不作为唯一事实来源。

Config 自身主要表达“用户拥有的配置资源”，不建议再让一个 `publish_status` 同时承担用户所有权状态、共享申请状态和广场展示状态。共享生命周期应由独立的广场准入记录表达。

### 5.2 Config Version

每次更新创建不可变版本，建议至少记录：

```text
version_id
config_id
version_number
storage_file_id
config_schema
schema_version
compatible_app_version / compatibility metadata
size_bytes
sha256
changelog
created_at
```

`current_version_id` 只指向当前对外版本；历史版本保留多久由容量与恢复策略决定。

### 5.3 底层 Storage Object

当前 `platform_config_files` 已经有成熟的不可变写入、hash、状态、未知写入、异步删除、配额结算和私有 Storage 机制。预研阶段不建议把这些安全语义重新实现一遍。

优先方向是：**将现有文件领域降级为 Config Version 的底层对象/存储账本**，在其上新增 Config 和 Version 业务层，而不是直接往 `platform_config_files` 继续堆发布、点赞、标题、审核字段。

是否最终重命名底层表，留到正式迁移设计决定。

### 5.4 广场准入记录 / Gallery Entry

建议新增独立的广场记录，作为“哪些配置被允许进入配置广场”的唯一事实来源。逻辑字段至少包括：

```text
gallery_entry_id
platform_id
config_id
approved_version_id
status                 # pending / approved / rejected / removed / blocked
submitted_at
submitted_by_account_id
reviewed_at
reviewed_by_admin_user_id
review_decision_code
removed_at
removed_by_admin_user_id
created_at
updated_at
```

关键不变量：

- `approved` 的 Gallery Entry 才能出现在配置广场。
- `approved_version_id` 必须属于同一个 Config、同一个平台，并且指向不可变 Config Version。
- 广场读取应以 Gallery Entry 为入口，不应扫描所有个人 Config 后靠 `visibility=true` 猜哪些能展示。
- 配置作者上传新版本时，不直接修改 `approved_version_id`；应产生新的审核请求，管理员批准后再原子切换广场展示版本。
- `removed / blocked` 只撤销共享展示资格；除非另有明确删除操作，否则用户个人 Config 与 Version 保留。
- 审核人、审核时间、决策和下架操作必须进入审计链路。

### 5.5 Like 唯一关系

点赞必须保存“谁给谁点过赞”，不能只维护一个 `likes + 1` 数字。

建议唯一关系：

```text
(platform_id, config_id, platform_account_id)
```

存在记录表示已点赞；取消点赞删除关系。`like_count` 可以事务内或异步维护成投影，但最终应能从关系恢复。

### 5.6 下载与应用事件

下载和一键应用需要分开统计，建议保留事件事实，再生成聚合计数。

至少区分：

- download requested / authorized / stream completed。
- apply requested。
- apply succeeded / failed（若 Consumer BFF 能提供可信结果回报）。

最终“下载量”和“应用量”的产品口径必须在正式合同中冻结。例如下载量更适合按成功完成的受控内容流计数，而不是按按钮点击计数；应用量不能把“拿到文件”直接等同于“目标平台应用成功”。

## 6. 作者身份与公开资料

当前 `platform_profiles` 已有 `display_name`、`avatar_url` 等平台内资料，可作为配置广场的作者展示来源，不另建第二套用户名系统。

建议广场默认展示作者当前 profile，而不是上传时的用户名快照；但审计记录应继续保存稳定的 `platform_account_id`，防止改名后无法追踪历史操作。

如果作者被 suspend / close / global delete，配置的可见性与内容保留必须有明确规则，不能只看当前 display name。

## 7. 配置格式、兼容性与一键应用

共享配置上线后，配置格式版本必须成为正式合同的一部分。建议每个 Consumer 平台定义自己的配置 schema，例如：

```text
config_schema = "aisenflow-config"
schema_version = 3
```

中央系统不需要理解业务 payload，但至少需要知道：

- 配置属于哪个平台。
- 使用哪个 schema。
- schema 版本。
- 可选的应用版本兼容范围。
- 内容大小与 hash。

Consumer 在一键应用前负责验证：

- schema 是否认识。
- 当前 App 版本是否兼容。
- payload 字段是否合法。
- 应用操作是否安全和可回滚（若平台自身支持）。

如果格式不兼容，应明确返回“配置版本不兼容”，不能由中央服务尝试转换未知 payload。

## 8. 个人配置、共享申请、广场准入、下架与删除是不同状态

后续不能再用一个文件 `status` 同时表达内容发布和 Storage 生命周期。

后续不能把这些概念塞进一个 `status`：

**个人 Config 生命周期**：

- Active：用户持有并可维护的个人配置。
- Deleting / Deleted：用户或授权治理动作明确删除个人配置，进入底层内容清理。

**广场准入生命周期**：

- Not Submitted：仅个人配置，未申请共享。
- Pending Review：作者已提交，等待管理员审核。
- Approved：管理员批准，指定版本进入广场。
- Rejected：管理员拒绝，本次申请不展示。
- Removed：管理员将已共享配置移出广场，但个人配置仍保留。
- Blocked：因违规/危险等治理原因禁止广场展示，可要求后续重新审核或禁止再次提交。

这使“管理员删除共享广场的文件”在产品语义上默认解释为**删除/移除广场条目（取消共享）**，不是删除用户个人配置。真正删除个人 Config 必须走独立的高风险治理操作并明确告知影响范围。

作者主动不再共享时，也应撤回/退出 Gallery Entry，而不是直接删除个人 Config。

## 9. Admin 产品形态

### 9.1 单平台 Admin：配置资源池

当前“文件”一级页面应改为更贴近产品的“配置资源”或“配置文件”。首屏关注平台资源状态，而不是 Storage 状态机。

建议摘要包括：

- 配置总数。
- 已发布配置数。
- 配置作者数。
- 周期新增配置。
- 点赞 / 下载 / 应用摘要。
- 平台配置存储使用量 / 分配额度。
- 待审核、被下架、异常写入等需要处理的数量。

其中 `Pending Review` 的广场共享申请属于平台管理员的核心待办，不应只存在于配置资源页。单平台概览也应提供“待审核配置”卡片，显示当前平台待审核申请数量；该数字必须由 Gallery Entry / 审核域的权威聚合产生，点击后直接进入配置资源的审核队列。若配置广场尚未接入，概览应显示“待接入/未启用”，不能以假 `0` 表示没有待审核事项。

配置资源池一级列表建议：

```text
配置名称 | 作者 | 共享审核状态 | 广场版本 | 大小 | 点赞 | 下载 | 应用 | 更新时间 | 操作
```

详情再展示：

- 历史版本。
- Storage object / path。
- SHA-256。
- 原始 file_id。
- write_outcome。
- 删除/恢复状态。
- 相关审计。
- 提交审核记录与历史审核决定。
- 批准进入广场 / 拒绝 / 移出广场 / 恢复准入等治理操作。
- 个人 Config 所有权与广场准入的边界提示，避免管理员误删用户私有内容。

### 9.2 全局 Admin：平台存储容量治理

全局平台管理需要新增 Storage Capacity 视角，用于：

- 给平台分配总容量。
- 查看平台已用/剩余空间。
- 识别接近容量上限的平台。
- 查看备份状态和异常。
- 必要时调整平台容量。

这一能力属于全局治理，不应重新放入单平台侧边栏的全局入口。

## 10. 安全与滥用控制

配置广场把原来的私有文件升级为用户生成内容，最低需要考虑：

- 标题和说明长度/字符限制，安全渲染，禁止脚本型注入。
- 单文件真实字节上限。
- Content-Type 不能作为可信安全判断。
- 平台/账户/Config/Version 使用复合归属关系，禁止跨平台引用。
- 上传、发版本、点赞、下载、应用接口的速率限制。
- 点赞唯一关系，防简单重复刷赞。
- 下载和应用统计按事件事实产生，避免浏览器任意提交计数。
- Admin 下架与删除写审计。
- 广场审核批准、拒绝、移出与恢复写审计，并记录管理员身份。
- 私有 Storage 不改成 public，不暴露 Secret 和永久对象 URL。
- 对 `unknown` 写入和异步删除继续保持 fail-closed，不猜测文件已不存在。

## 11. 用户关闭账户与全局删除

这是正式架构必须冻结的高风险边界。

当前文件系统会参与账户关闭和 Global Delete，新的公开 Config 又可能已经被其他用户点赞、下载和应用。不能因为它“公开过”就默认永久保留作者数据。

预研建议采用保守默认：

- Global Delete 时先停止新的公开访问/发布。
- 作者拥有的 Config 进入下架和内容删除流程。
- Profile 等个人资料继续按现有身份清除规则处理。
- 他人点赞关系、统计事件中涉及身份的部分按隐私模型匿名化或清除。
- 若未来希望“作者删除账户后作品匿名保留”，必须单独形成产品、隐私和数据保留决定，不能作为默认行为。

## 12. 备份与恢复

现有仓库已经有 `file_backup_barriers`、manifest 和删除屏障合同，但它们只证明“数据库有协调备份的协议”，不能证明真实外部恢复介质已经存在。

配置成为共享用户内容后，正式备份范围至少应覆盖：

- Config metadata。
- Config Version metadata。
- 对应的私有 Storage Objects。
- 当前版本指针和发布/审核状态。
- 必要的点赞关系或可恢复的互动事件。

统计投影如果可从事件重建，可以不作为唯一备份事实，但其源事件需要进入恢复范围。

未来 Admin 只有在确实存在外部备份和恢复验证后，才可以展示：

- 最近成功备份时间。
- Recovery Set / Manifest。
- 覆盖范围。
- 最近恢复演练结果。
- 失败告警。

在这之前只能显示“未配置 / 无法验证外部备份”，不能显示虚假的绿色“已备份”。

## 13. 从现有实现迁移的原则

正式实施计划尚未制定，但迁移方向应遵守：

1. 不直接破坏现有 `platform_config_files` 的安全状态机。
2. 新增 Config / Version 业务层后，让 Version 关联底层文件对象。
3. 现有用户私有配置默认不能自动进入配置广场；迁移后统一视为个人 Config，不创建 `approved` Gallery Entry。
4. 对已有 replace 链、active 文件和历史对象做数据调查后，再决定如何映射为 Config 与 Version；无法可靠推断的文件保持私有，不猜测作品关系。
5. 新旧 API 迁移期不得存在两套互相矛盾的配额与删除算法。
6. 正式切换前要冻结新的 entitlement feature、平台容量合同、Config 生命周期、Gallery Entry 审核生命周期和 API 语义。

## 14. 正式架构阶段需要继续确定的问题

以下问题保留到正式 design/plan 阶段做源码与产品联合决策：

1. Config 槽位限制统计 Draft、Published 还是全部未删除 Config；预研倾向统计全部有效 Config，避免通过反复下架绕过额度。
2. 套餐降级超额后，是否允许为已有 Config 发布修复版本；预研倾向允许维护已有 Config、禁止创建新 Config。
3. 每个 Config 保留多少历史版本、多久清理，以及是否允许作者回滚。
4. 平台总容量默认值、最小/最大值和扩容权限。
5. 下载量和应用量的精确定义、幂等键和反刷规则。
6. 一键应用成功结果由 Consumer BFF 如何可信回报。
7. Config schema/version 如何在 Consumer 接入合同中注册和验证。
8. Admin 广场审核的第一版范围：提交、批准、拒绝、移出、恢复、Blocked 以及审核原因/审计口径。
9. 作者上传新版本后的审核策略；预研倾向广场继续展示最后一个已批准版本，新版本必须重新审核后才能替换。
10. Global Delete 后是否存在任何“匿名保留公开作品”的业务需求；未明确前按删除处理。
11. 外部 Storage 备份目标、RPO/RTO 和恢复演练实现。
