# 如何编写模块优化计划

本文件规定 `docs/proposals/<优化名称>/` 内计划文档的写法。它服务于当前 Aisenhubplatform 的模块优化，不替代当前架构文档、API 合同或数据库迁移。

## 什么时候建立 Proposal

当改动会改变模块边界、数据流、数据库模型、API、权限、状态机、持久任务、SDK 合同、页面流程或部署依赖时，建立一个独立 Proposal。只改一个局部实现且不改变这些边界时，可以直接修改代码和对应参考文档。

目录名使用小写短横线，例如：

```text
docs/proposals/account-auth-optimization/
├── design.md
├── plan.md
├── phases/
│   ├── 01-contract-and-probe.md
│   └── 02-implementation.md
├── agent-handoff.md
└── verification-record.md
```

`design.md` 说明要把系统变成什么样，`plan.md` 说明如何分阶段完成，`phases/` 说明 Agent 每一阶段具体改什么和如何验收。`agent-handoff.md` 和 `verification-record.md` 放在 Proposal 根目录，分别作为稳定执行入口和实施期间的事实记录。

## 写作顺序

先从代码、迁移、配置和测试中建立当前事实，再写目标设计，最后拆分实施阶段。架构事实引用 `docs/architecture/`，接口引用 `docs/reference/contracts/` 和共享类型，数据库字段引用 `supabase/migrations/`；不要把同一套定义复制到多个计划文件。

如果发现当前文档与代码冲突，在计划中列出文件、代码证据、影响和处理方式。当前行为以代码为准，目标行为以已确定的优化方向为准；无法核实的内容写成待验证，不用推测填空。

## design.md 应回答的问题

- 用户或系统现在遇到什么具体问题？
- 当前调用链和模块边界是什么？哪些是代码已有能力，哪些只是目标？
- 本次优化要达到什么可观察行为？明确非目标是什么？
- 模块、数据流、状态和职责准备如何变化？
- Account/Auth、Admin、Maintenance、Storage、SDK 或页面之间的边界如何保持？
- API、共享类型、数据库迁移、配置、消费者和部署会怎样变化？
- 哪些权限、并发、失败恢复、兼容或数据保留风险需要处理？
- 哪些决定已冻结，哪些问题需要早期实验或用户确认？

目标架构必须标注“尚未实现”，直到代码真正生效。只有新结构成为实际运行路径后，才同步 `docs/architecture/`。

## plan.md 应回答的问题

总计划至少包含：

1. 目标、范围和非目标。
2. 当前代码证据和关键缺口。
3. 已冻结的架构、数据、接口和状态契约。
4. 阶段列表、前置依赖、交付物、状态和阶段链接。
5. 可以并行的工作、必须串行的工作及集成人。
6. 全局约束、风险、阻塞处理和完成标准。
7. 每阶段的验证、文档同步、commit 和 push 门槛。

阶段不是按“前端、后端、测试”机械切分，而是按可独立验收的结果切分。跨阶段共享迁移、OpenAPI、共享类型、状态机和领域函数必须在早期阶段冻结，避免多个 Agent 各自发明一套规则。

## 阶段计划应写到什么程度

每份阶段计划都要让没有参与讨论的 Agent 能够开始工作。至少包括：

- 目标、进入条件、必读文档和上游交接。
- 已核实文件、入口函数、页面和真实调用链。
- 需要修改或新增的文件，以及每个文件的职责。
- 应复用的现有能力和明确禁止复制的实现。
- 数据模型、接口、输入输出、状态转换和不变量。
- 按依赖排序的实施步骤，而不是“完善、优化、支持”等抽象句子。
- 适用的正常、空态、加载、失败、禁用、冲突、重试和恢复行为。
- 相邻模块影响、旧路径退出、双写避免和兼容策略。
- 实际存在的验证命令、环境、预期观察结果和阶段退出条件。
- 交给下一阶段的接口、提交、记录和未解决问题。

例如，文件上传阶段应写明 `upload-intent`、有界字节读取、Storage 写入前校验、`write_outcome`、租约、预算和 unknown 结果如何验证；不能只写“完善上传异常处理”。权益阶段应引用 PostgreSQL private 领域过程和 Ledger/Event/Projection 关系；不能让页面或 SDK 自行计算权益。

## 状态和验证记录

Proposal 状态使用 `Proposed`、`In Progress`、`Completed`。阶段状态使用 `未开始`、`进行中`、`已阻塞`、`验证失败`、`验收通过待推送`、`已交付`。

`已交付` 必须同时满足代码实施完成、必要验收通过、阶段提交已 push 且远端 commit 已核对。代码已写但未验证、已提交但未 push、或只有静态检查通过，都不能写成已交付。

计划文档只写预期和门槛；实际执行命令、退出码、失败原因、复测、提交和远端状态写入 `verification-record.md`。验证记录不能预填 PASS、完成状态、commit SHA 或推送成功，也不能把失败记录改写成从未发生。

## 当前项目的固定约束

- 保持 pnpm、TypeScript、Next.js、Supabase、PostgreSQL、Deno、Tailwind 和 shadcn 基础设施。
- 当前领域规则的唯一写入口是 PostgreSQL private 函数；Account API、Admin 和 Maintenance 通过受控 executor 调用。
- 平台和账户关系必须保持租户边界；不能信任请求 body 中的归属字段。
- 私有 Storage 只由服务端代理访问；不能在浏览器暴露 Secret、SQL 凭据、Platform Key 或 HMAC。
- OpenAPI、共享 DTO、数据库迁移、消费者和测试必须同步；不随意重命名跨模块字段。
- 本地操作使用仓库脚本，并遵守根 AGENTS.md 的路径和缓存规则；不把生产 URL、真实凭据或用户数据写入计划。
- 每阶段必要验证、commit 和 push 是交付门槛；不 force push、不重写已有历史、不把 push 等同于部署。

## 编写完成检查表

- [ ] 当前架构与目标架构已分开。
- [ ] 目标、范围、非目标和交付标准明确。
- [ ] 当前代码证据、文件路径和调用链可核对。
- [ ] 跨阶段数据、接口、状态和时间语义只有一个来源。
- [ ] 每个阶段都有进入条件、具体步骤、验证和退出条件。
- [ ] 未实现、待验证和外部依赖没有写成既成事实。
- [ ] `agent-handoff.md` 与 `verification-record.md` 已建立。
- [ ] 文档链接有效，计划依赖无环。

计划生成阶段不执行 Git 提交、推送、部署或产品改造；这些动作只在后续实施 Agent 按交接文件和阶段门槛执行。
