# D1/D2/D3 决策对比与已确认规则

本文件把 Subscription Billing Centralization 中仍影响实现的三个业务决策集中记录。D1、D2、D3 均按 2026-09-14/15 业务确认更新；删除匿名化的具体保留天数仍由法务/财务通过受控配置提供，不以代码默认值替代业务或法律决定。

## 决策结论摘要

| 决策 | 当前结论 | 对实现的直接影响 | 状态 |
| --- | --- | --- | --- |
| D1：99 年商品再次购买 | 允许。同一 Plan 的每次成功付款都在当前到期时间之后增加 99 年；不同有效 Plan 仍按冲突规则处理 | 移除“Lifetime 只能购买一次”的业务阻断；保留并发幂等、历史订单不可改；Checkout 前展示额外打赏确认 | 已确认 |
| D2：退款 | 网站不提供退款；购买权益即表示对开发者的打赏；不调用 Provider 退款 API，不因普通退款请求自动撤销权益 | 退款/拒付/Provider 侧逆向资金事实仍需记录为异常并进入人工复核，不得伪造为正常退款完成 | 已确认（须遵守适用法律及支付平台强制规则） |
| D3：暂停、删除保留、Plan 归档 | 暂停立即阻止新购买但已有有限期权益继续；删除保留最小账务/审计事实并按法定/财务期限匿名化；归档阻止新 Checkout 但保留历史订单、快照和权益，旧 Plan 不再修改 | 冻结生命周期锁序、保留期限配置、匿名字段和归档后的只读行为 | 已确认（保留天数需配置） |

## D1：99 年商品是否允许再次购买

### 已确认规则

1. 同一用户、同一平台、同一 Plan 的 99 年商品允许再次购买。
2. 每次成功付款产生独立的 Billing Order、Settlement、Grant/Event 事实；不得覆盖或修改历史订单。
3. 新 Grant 的开始时间取 `greatest(now(), 当前同 Plan 有效权益的结束时间)`，结束时间在此基础上再增加 99 年。
4. 不同仍有效的 Plan 继续拒绝或进入现有冲突处理流程，不因 D1 放宽成跨 Plan 叠加。
5. 付款前必须以弹窗或等价的显式确认提示用户：再次付款代表对开发者的额外打赏，并会在当前权益基础上增加年限；用户确认状态必须随 Checkout 意图留痕。
6. 同一 Idempotency-Key、重复 Webhook、并发结算仍只能产生一份对应订单事实和一份对应 Grant；不同付款意图可以产生不同订单。

### 实现与验收

- Forward-fix `billing_lifetime_purchase_guard`，删除同账户第二笔 Lifetime 的旧阻断，但保留 pending/expired Checkout 的恢复和并发锁。
- 结算入口必须把 99 年视为有限期限，不得写入 `ends_at = null`，也不得走 Admin 真永久权益分支。
- Consumer 在创建 Checkout 前展示确认弹窗；取消时不创建新的支付意图。
- SQL 负例：同 Plan 第二笔成功付款不得触发 `lifetime_already_purchased`，最终结束时间增加 99 年；不同 Plan 仍冲突；重复 Webhook 不新增 Grant。
- Provider/Staging 仍需验证真实商品、旧链接、迟到 paid 和多次付款的资金事实，Local 结果不能替代。

## D2：退款、撤权和 Provider 退款 API

### 已确认规则

网站产品规则为“不退款”：用户选择权益即视为对开发者的打赏，网站不提供普通退款入口，不调用 Provider 退款 API，也不因普通用户请求自动撤销已授予权益。

该规则不等于可以丢弃外部资金事实。以下情况仍必须进入 Billing 异常链路：

- Provider 或支付平台实际产生退款、拒付或冲正；
- Provider 侧金额已经逆向，但本地 Settlement/Grant 仍显示已完成；
- 运营人员在后台确认了例外补偿。

这些情况只记录标准化 refund observation 和人工处理状态；没有 D2 以外的授权时，不自动调用退款、撤销权益或创建替代 Grant。

### 实现与验收

- 保留退款观察事实、Provider refund ID、原订单、金额、币种、观测时间和补偿状态。
- `compensation_pending` 进入告警和 Admin 人工队列；`compensated` 必须绑定明确 operation ID，不允许只改展示状态。
- 普通用户退款请求返回清晰的“不提供退款”说明，不泄露内部 Provider 或账务细节。
- Provider 真实退款/拒付演练由 Staging/Provider 环境完成；不得用 Local fixture 宣称资金链路通过。
- 产品文案和法律/支付平台强制退款权冲突时，以适用法律及平台规则为准，并由业务/法务确认后更新本决策。

## D3：生命周期策略（通俗解释）

### 1. “暂停何时生效”是什么意思

当平台或订阅被暂停时，需要明确两件事：

- 是马上禁止新购买、马上停止访问，还是等当前已购买权益到期后再停止；
- 暂停期间 Provider 已支付但尚未结算的订单，是继续处理、进入人工队列，还是暂时冻结。

已确认：暂停立即禁止新的付费 Checkout；已有有限期权益继续到原定结束时间，已付款事实继续进入结算和对账，不因为暂停被静默丢弃。暂停是购买闸门，不等同于平台停用，因此不能连带阻断已有权益读取。

### 2. “删除/匿名化保留周期”是什么意思

用户删除账号后，订单、金额、Provider 订单号、审计记录可能仍需要保留一段时间用于财务、争议和安全审计。但不应无限期保留邮箱、姓名、Provider 用户标识等个人信息。

实现约束：

- 哪些字段属于必须保留的账务证据；
- 个人字段何时匿名化或删除；
- 订单事实与匿名后的账户如何继续关联；
- 该周期结束后是否允许彻底删除关联数据。

已确认：保留最小化的账务和审计事实，个人字段在适用法定/财务保留期结束后匿名化。代码通过 `private.account_retention_policy` 接收天数、来源和依据；未配置时清理任务失败关闭，不猜测年数。

### 3. “Plan 归档规则”是什么意思

Plan 归档表示该 Plan 不再允许新购买，但历史订单、历史价格快照和已经发放的权益仍然可追溯。归档不能通过修改原 Plan 的价格来重写历史交易。

已确认：归档立即阻止新 Checkout；已有 Grant 按原快照继续生效至结束；历史订单、价格快照和 Admin 详情保留；归档后的旧 Plan 进入不可变终态，需要变更商业条款时发布新 Plan/mapping 版本。

### D3 已确认表

| 项目 | 建议默认值 | 需要确认的内容 |
| --- | --- | --- |
| 暂停 | 立即禁止新付费 Checkout；已有有限期权益继续；已付款继续结算 | 仅需在 Provider/Hosted 演练中验证异常订单处置 |
| 删除 | 账务/审计最小事实保留；个人字段按法定/财务期限匿名化 | 法务/财务需提供实际天数、来源与依据并写入受控配置 |
| Plan 归档 | 禁止新 Checkout；历史订单、快照、已有权益保留；旧 Plan 不可修改 | 不允许通过旧 Plan 补购；新商业条款发布新 Plan |

## 未由本文件替代的外部门槛

D1/D2 的确认只解决业务规则，不等于 Provider、Hosted、Staging 或 Production 验收通过。真实商品、退款/拒付事实、密钥、Cron、网关、备份、告警接收和生产发布仍需相应环境证据与批准。
