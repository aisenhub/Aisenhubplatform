## 审核结论

当前 `T17.md`/`G0-S.md` 只有 Staging 基础 Auth/Account API 快照：默认
`SUPABASE_DB_URL` 没有证明 Account/Admin 独立身份、事务 pooler、TLS
验证或连接回收合同。X02 的托管站点、代理链和可用于 SQL 角色/TLS 核验的
受控 Staging 输入也未在本轮提供，因此不能把历史 Edge ACTIVE 或 Local
角色探针写成 T17-R1 PASS。

本轮按既有安全合同修正了两处可独立交付的代码：

- `supabase/config.toml` 将 `account-api` 的 `verify_jwt` 改为 `false`。
  该函数同时承载不带用户 JWT 的平台 Key 套餐查询和用户/Admin 路由，
  由 `index.ts` 对每条路由执行 Platform Key、Auth session、AAL2 和
  step-up 检查；关闭旧式网关预验证不开放匿名业务访问。
- `supabase/functions/account-api/index.ts` 按请求类型优先读取
  `ACCOUNT_DB_URL` 或 `ADMIN_DB_URL`，分别缓存连接；Local 仍回退到
  `ACCOUNT_API_DB_URL`/`SUPABASE_DB_URL`。两类事务继续使用
  `prepare: false` 并在事务内设置对应 executor role。

## 固定托管配置规格

托管发布前必须由项目所有者在 Secret Manager 提供以下独立变量，变量值、
密码、CA 内容不得进入仓库或报告：

| 入口 | 用途 | 必须证明 |
|---|---|---|
| `ACCOUNT_DB_URL` | Account API 用户/公开套餐路由 | 独立 LOGIN 身份只能进入 account executor 能力 |
| `ADMIN_DB_URL` | Account API Admin 路由 | 独立 LOGIN 身份只能进入 admin executor 能力 |
| `JOB_DB_URL` | 后台任务（由对应任务入口消费） | 不可调用普通 Account/Admin 入口 |

运行时连接使用项目 Dashboard 提供的真实 pooler 地址，不手工推测主机名。
Serverless/Edge 使用 transaction pooler 时使用端口 `6543`、关闭 prepared
statements，并以 `sslmode=verify-full` 配合项目 CA；迁移和管理工具不复用
运行时凭据。连接必须在短事务结束后显式释放，不能依赖跨请求 session 状态。

## 发布请求矩阵

在受控 Staging 重新部署后，逐条保存脱敏状态码、业务错误码、请求 ID 和
版本，不保存 token、Key 或 Cookie：

| 请求 | 预期 |
|---|---|
| `GET /functions/v1/account-api/v1/plans` + 有效 `X-Platform-Key`、无用户 JWT | `200`，只返回 active 套餐 |
| 同上，缺失/格式错误/撤销/未知版本 Platform Key | `401`，或按合同返回 `403`/稳定错误码 |
| Account 路由缺失、伪造或 Auth 未验证的 Bearer token | `401`，且不进入业务函数 |
| Account 路由有效 Platform Key + 有效 session | 按 Principal/账户状态返回合同结果 |
| Admin 路由缺失 JWT、AAL1 或缺少近期 step-up | `401`/`403`，不得执行 Admin SQL |
| 已认证请求命中未知 path/method | `404 RESOURCE_NOT_FOUND` |

## 必须执行的 SQL/连接证据

每个入口至少一次真实连接核对：`current_user`/`session_user`、当前连接
是否 TLS、协议版本/密码套件、pooler 端口、连接回收；角色目录核对
`rolcanlogin`、`rolbypassrls`、角色成员关系及所需函数 EXECUTE，负向核对
基础表 DML、Auth schema、另一 executor 和内部 claim/finalize/audit helper
均被拒绝。所有连接字符串通过受控 Secret 注入，不能用默认高权限
`SUPABASE_DB_URL` 代替独立入口。
