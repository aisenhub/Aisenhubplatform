## 当前结论

本任务为 **PARTIAL**。

已交付 Admin 的真实 MFA 消费链：登录后进入 MFA 页面；服务端用当前 HttpOnly session 恢复请求级 Auth client，列出已验证 TOTP 因子，调用官方 `auth.mfa.challengeAndVerify`，再使用升级后的 session 调用中央已登记的 `/admin/api/v1/auth/recent-proof`。中央成功返回并校验 UUID proof 后，才写入绑定 Admin 会话的 HttpOnly、5 分钟 proof cookie；proof 不接受浏览器提交的任意值。

中央 Account API 现对除 recent-proof 签发路由外的所有 Admin 路由统一拒绝 AAL1。敏感写操作仍由 `private.admin_step_up_valid` 再次实时检查 user/session/proof，refresh 不延长 proof 窗口，logout 清除本地 proof 并撤销 Auth 会话。

普通用户 reauthentication 的 SDK 适配已补入 Auth 包，但普通用户 proof 仍未签发。按 Supabase 官方合同，`reauthenticate()` 发送供后续 `updateUser({ password, nonce })` 使用的 nonce，并没有可供敏感操作单独消费的 `verifyOtp(type='reauthentication')` 事件验证入口；对 `/auth/v1/verify` 的实测返回 `otp_expired`。因此没有新增未登记 endpoint、迁移或伪造 issuer，也没有用 JWT `iat`、AAL2 或前端状态替代事件证明；Close 与 Global Delete request 继续在没有服务端 proof 时拒绝。
