## 当前结论

本任务为 **PASS（Local）**。完整 Close/Global Delete request HTTP 消费者仍由 T16-R1 承接；本任务交付并验证其所依赖的近期认证协议与 Admin MFA 闭环。

已交付 Admin 的真实 MFA 消费链：登录后进入 MFA 页面；服务端用当前 HttpOnly session 恢复请求级 Auth client，列出已验证 TOTP 因子，调用官方 `auth.mfa.challengeAndVerify`，再使用升级后的 session 调用中央已登记的 `/admin/api/v1/auth/recent-proof`。中央成功返回并校验 UUID proof 后，才写入绑定 Admin 会话的 HttpOnly、5 分钟 proof cookie；proof 不接受浏览器提交的任意值。

中央 Account API 现对除 recent-proof 签发路由外的所有 Admin 路由统一拒绝 AAL1。敏感写操作仍由 `private.admin_step_up_valid` 再次实时检查 user/session/proof，refresh 不延长 proof 窗口，logout 清除本地 proof 并撤销 Auth 会话。

普通用户近期认证现采用已在 Local Auth 实测的独立 email sign-in 事件：BFF 从当前 HttpOnly 会话取得并确认邮箱，调用 `signInWithOtp({ shouldCreateUser: false })`；用户提交邮件中的 `token_hash` 后，BFF 在不持久化的临时 Auth client 中调用 `verifyOtp({ token_hash, type: 'email' })`。中央 Account API 同时验证当前 bearer 与 `X-Reauth-Access-Token` 的用户、session_id，再由窄范围 security-definer helper 查询 `auth.sessions` 的同用户、5分钟内、未过期事件；proof 只绑定原业务 session。BFF 不向浏览器返回临时 session，并在成功/失败路径结束时撤销临时 session。旧的 `reauthenticate()`/nonce helper 保留为 Supabase 资料或密码变更语义，不被当作敏感操作 proof。
