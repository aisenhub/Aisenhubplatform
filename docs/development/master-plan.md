# 开发总计划 DP2

基线：[Architecture v1.2](../architecture.md)。目标是交付可复用、可运营的自营多平台账户后端；不扩大到支付、组织、第三方平台或微服务。

## 1. 当前状态与本轮产出

2026-09-08校准：已有工程、包锁、迁移、CI及M1/M2/M3的分范围Local交付；T12/T16/T17仍PARTIAL，G2-L需正式收口，G0-S/G2-S尚未完整通过，M4～M6未实施。应用实现已推送任务分支，尚未合入main。见[实际进度](status.md)及[DP2校准证据](evidence/DP2-baseline.md)。

DP1建立M0～M6规格与前两批任务；本轮DP2校准进度，新增[首批收尾](tasks/closeout-01.md)、[M4第三批](tasks/batch-03.md)及[M5/M6路线](roadmap-dp2.md)。这是规划授权，不自动执行应用实现、购买服务、合并或部署。

## 2. 交付结果与非目标

最终可从Admin创建平台、Origin、Plan、文件策略及平台Key；消费应用只安装SDK/模板和配置即可接入，完成认证、激活、Profile、权益、兑换、文件及停用授权。至少两个不同Origin消费入口验证共享身份与平台状态隔离。

Admin必须单一管理员、AAL2与近期MFA；业务使用统一数据库过程。代码提交不是业务验收，模块不能以“UI可点”代替数据不变量和失败恢复证明。

不新增Billing/Team/RBAC，不重建Supabase Auth，不把未来能力占位实现成未经设计的公共接口。可视化/品牌精修在功能合同稳定后进行，不阻塞安全核心。

## 4. 实施里程碑

| 里程碑 | 可演示结果 | 不得缺少的证据 |

| P0 本地工程可运行 | Admin空壳、Consumer空壳、本地Supabase，CI工作流 | 版本清单、clean install/build、探针结果 |

| P2 权益纵向链路 | 创建套餐/批次→确认交付→用户兑换→业务读取权益 | 多码并发、事务回滚、幂等、重放 |
| P3 文件纵向链路 | 意图→受控字节→私有对象→后端下载→异步删除 | 真字节超限无Storage调用，配额及未知写入故障测试 |

不承诺未经工具验证的工期。每个任务以独立验收行为切分；出现超过一个公共合同变化或多个难以回滚的迁移时继续拆分，不把数周工作藏进一个“实现模块”任务。

## 5. 公共合同先行

M1固定private SQL函数边界、Context来源、审计/幂等结果约定；M2固定OpenAPI/共享类型、BFF验证与SDK调用。M3/M4在已有外壳中扩展对应资源，不能私自更改其他模块路径、错误码或JSON命名。

HTTP对外用架构定义的字段；SQL用snake_case；现有Principal TypeScript字段保留camelCase。转换仅在adapter，测试比较真实序列化结果。未来函数名、ownership与请求细节由本轮公共合同表指定。

日期与Grant效果由Postgres领域过程唯一计算。共享TypeScript只提供验证、DTO、错误映射和测试输入，不能建立第二套生产权益计算器。参考实现仅可出现在测试目录且必须标注用途。

## 6. 测试与完成定义

每个任务完成必须满足：

1. 任务范围内行为实现，改动局限于约定目录或已记录的必要共享合同。
2. 相应V-*用例实际通过；必要负向、并发和故障路径不能标NOT_RUN后宣称DONE。
3. 迁移空库与权限验证通过，SQL角色测试不是用postgres代替。
4. 文档/类型/SDK/示例同步；无Secret或真实业务数据进入日志和仓库。
5. 已提交任务commit；阶段要求push时核对远端SHA。完成报告给出复现命令、环境、测试摘要及局限。

详细用例见[验证计划](verification-plan.md)。正式应用检查命令由M0建立：format:check、lint、typecheck、test:unit、test:db、test:api、test:e2e、build；在package.json实际落地之前这些只是约定名称。

## 7. GitHub阶段同步

仓库：[aisenhub/Aisenhubplatform](https://github.com/aisenhub/Aisenhubplatform)。main仍在规划基线；应用代码位于已推送任务分支。DP2从已实现基线派生，最终集成需要审查完整应用差异，不将文档分支误当作只有文档历史。

DP1历史分C1架构、C2总计划、C3规格任务三个阶段推送，记录见status。本轮DP2作为独立规划交付提交并核对远端；后续每阶段记录commit与远端确认，不强推。

后续应用任务默认task/<任务ID>-<简短名称>分支，任务验收后commit/push；模块集成通过后PR进入main。检查已有branch protection，不自动绕过。只有明确有合并授权时执行merge；阶段push本身不等于生产部署授权。

PR说明以实际行为和验证为主，包含任务ID/模块/相关决策。上游导入不覆盖本仓库README、AGENTS、docs或Git历史。

## 8. 外部依赖和决策管理

见[决策登记](decision-register.md)。已确认架构规则是硬约束；限流、容量、保留期限及恢复目标是工程默认/待业务确认参数。允许按默认值完成本地实现和测试；相关生产门槛必须在外部输入确认后关闭。

Staging凭据、Google OAuth、SMTP、域名、备份存储和告警渠道缺失时，记录具体需求与被阻塞用例，不把缺失归咎于代码，也不使用生产凭据临时代替。

技术验证发现问题时，先更新决策、对应架构专题和受影响任务，再实现替代路径；禁止静默增加service-role DB访问、放宽MFA、直传文件或跨请求授权缓存。
